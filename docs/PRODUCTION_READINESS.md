## 2. Outstanding issues

- **Single instance only.** Rate limiters, the SSE event bus, run locks, execution jobs, live previews, and autonomous pipeline runs are in-process. The PostgreSQL advisory lock enforces one API replica per database; a second instance refuses to start. Multi-instance deployment requires shared job/preview state and per-host workspace volumes; a pipeline run started on one instance is invisible to another.
- **Preview processes are in-memory.** Active previews and their tokens do not survive an API restart; users start them again from the workspace (the TTL sweeper finalizes them as expired on next access). Token revocation on project delete happens in memory only.
- **Session tokens are stored verbatim** in the store (JSON file or PostgreSQL `sessions.doc`), not as hashes — a store-database leak would expose live tokens until expiry. Hashing at rest requires migrating persisted sessions and is the top follow-up hardening item. Mitigations: httpOnly cookies (opt-in) keep the token out of the browser entirely; session lifetime is bounded (8h/30d); the store file must be protected like the database.
- **Sandbox scope.** Bubblewrap isolation (pid/net/ipc/uts/user/cgroup namespaces, read-only host) is strong but unhardened: it is not a seccomp-guaranteed boundary and depends on a correct host mount table. Prefer dedicated nodes or VMs for untrusted work; keep `HELIX_WORKSPACE_ROOT` off the API's system volume.
- **Repo-wide Prettier errors** remain across files not touched by this work (`npm run lint`: formatting only); run `npm run format` in a dedicated PR. All files touched by the mission stages are eslint/prettier clean.
- **Live provider verification remains blocked on credentials.** No vendor keys exist in this environment. The provider path is verified against local OpenAI-compatible contract servers (real HTTP transport, auth headers, retries, JSON contract; scripted model responses) — this is local-endpoint verification of the platform loop, **not** a claim about live-vendor model quality. `npm run verify:providers` is the deploy gate: run it with real keys before serving traffic (see DEPLOYMENT.md).

## 4. Deployment requirements

See **`DEPLOYMENT.md`** for the full guide (configuration reference, database setup, monitoring, backups, pre-launch checklist). Summary:

- Node.js 22+; Linux host with `bubblewrap` (`bwrap`) on PATH and `/usr/bin/prlimit` for sandboxed execution; execution and preview degrade to a clear unavailable status without them.
- `NODE_ENV=production`, a strong random `JWT_SECRET`, `BASE_URL`, `CORS_ORIGINS` (also scopes preview `frame-ancestors`).
- `DATABASE_URL` (PostgreSQL 13+) — migrations run automatically on boot; one API replica per database.
- `HELIX_WORKSPACE_ROOT` on a persistent volume (per-project, deletable).
- At least one AI provider key (`GOOGLE_AI_API_KEY`, `AI_API_KEY` for OpenAI, or `XAI_API_KEY`), optionally `AI_FALLBACK_PROVIDERS`. Keep `HELIX_ALLOW_MOCK_FALLBACK=false` in production and gate the launch on `npm run verify:providers`.
- Size `HELIX_USER_DAILY_TOKEN_LIMIT` / `HELIX_PROJECT_DAILY_TOKEN_LIMIT` / `HELIX_AI_RATE_LIMIT_MAX` to the user base; decide the `HELIX_AUTONOMOUS_AUTO_APPROVE` posture explicitly (default: rejected in production).
- Email: `EMAIL_PROVIDER=smtp|sendgrid` with credentials (the `demo` provider exposes tokens in responses outside production only).
- OAuth (optional): `GOOGLE_CLIENT_ID/SECRET`, `GITHUB_CLIENT_ID/SECRET` and matching `VITE_*` client IDs.
- Reverse proxy must not buffer `text/event-stream` (the API sends `X-Accel-Buffering: no`) and must preserve the preview path prefix (`/api/v1/projects/:id/preview/:token/...`).
- Start the API with `npm run start:api`; build the frontend with `npm run build`.
